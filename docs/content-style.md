# 강의 콘텐츠 작성 규칙

`docs/lecture/**/*.md`(STEP 01~12·부록·보충)에 적용한다. 2026-11-03~04 사용자가 직접 지시·정정한 수정 패턴(#43·#44·#53·#56, 커밋 `0a61a38`·`14f9dca`·`b982b68`·`879bc91`·`b0f8e22`·`4cdaac1`)을 규칙으로 정리했다. 각 규칙은 규칙 → 잘못된 예 → 고친 예 → 이유 순서다. 결정론적으로 검사할 수 있는 항목은 끝의 검사 스크립트로 확인한다.

## 1. 문체

### 1-1. 평서체로 쓴다
- 규칙: 본문·목록·표의 서술은 `~다`로 끝낸다. `~습니다`·`~입니다`·`~세요`·`~십시오`는 쓰지 않는다. 코드 블록·인라인 코드·HTML 예시 안의 문구는 예외다.
- 잘못된 예: `Git은 파일 변경을 무작정 저장하지 않고 명확한 3단계를 거칩니다.`
- 고친 예: `Git은 파일 변경을 무작정 저장하지 않고 확실히 구분되는 3단계를 거친다.`
- 이유: 사이트·PDF 전체 톤을 간결하게 통일한다(#53). 오변환 주의: `괜찮다`·`적다`·`다르다`·`보인다`처럼 형용사·자동사는 `~는다`로 바꾸지 않는다.

### 1-2. 단정을 완화한다
- 규칙: 항상 그렇다고 보장할 수 없는 결과는 `~할 수 있다`로 쓴다. 공포 조성형 단정은 피한다.
- 잘못된 예: `이러한 수동 복사 방식은 다음과 같은 치명적인 문제를 낳는다:`
- 고친 예: `이러한 수동 복사 방식은 다음과 같은 치명적인 문제를 발생시킬 수 있다:`
- 이유: 가능성과 필연을 구분해야 학습자가 실제 상황을 판단할 수 있다(`b0f8e22`).

### 1-3. 상태를 단정하지 않고 확인 절차를 쓴다
- 규칙: 환경에 따라 달라지는 사실(설치 여부 등)은 단정하지 않고 확인 명령과 조치를 안내한다.
- 잘못된 예: `macOS에는 Git이 이미 설치되어 있다.`
- 고친 예: `터미널에서 git --version을 실행해 설치 상태를 확인하고, 없으면 개발자 도구 설치 안내를 따른다.`
- 이유: 공식 문서도 보장하지 않는 전제를 강의가 보장하면 트러블 슈팅이 어긋난다(#56).

## 2. 용어

### 2-1. 뜻이 정확한 단어를 고른다
- 규칙: 사람의 인지 상태는 `혼동`, 여러 주체가 뒤섞이는 상황은 `혼선`으로 구분한다. `명확한`처럼 범용 수식어 대신 구조를 드러내는 표현을 쓴다.
- 잘못된 예: `**최신 파일 혼선**` / `명확한 3단계를 거친다`
- 고친 예: `**최신 파일 혼동**` / `확실히 구분되는 3단계를 거친다`
- 이유: 학습자가 어떤 파일이 최신인지 헷갈리는 것은 혼동이다. "확실히 구분되는"은 세 영역이 서로 다른 단계라는 사실 자체를 전달한다(`4cdaac1`).

### 2-2. 특정 기술에 한정하지 않는다
- 규칙: Git 개념을 설명할 때 예시 기술(CSS·HTML·웹페이지)을 개념 문장에 끌어오지 않는다. 실습 코드 설명에서는 기술명을 그대로 쓴다.
- 잘못된 예: `어떤 CSS 코드나 문구가 바뀌었는지` / `웹페이지를 제작하다 보면 … 레이아웃 CSS를 조금 수정했는데 화면 배치가 깨져서`
- 고친 예: `어떤 코드나 문구가 바뀌었는지` / `프로그래밍을 하다 보면 … 코드를 조금 수정했는데 실행이 안 돼서`
- 이유: 과정의 대상은 Git이며 웹 실습은 수단이다. 개념 문장을 일반화해야 다른 언어·프로젝트에도 그대로 적용된다(`879bc91`·`4cdaac1`).

### 2-3. 범위를 정확하게 쓴다
- 규칙: Git이 다루는 범위는 "컴퓨터 전체"가 아니라 "Git이 관리하는 폴더(저장소)"다.
- 잘못된 예: `내 컴퓨터 안에서 파일이 이동하는 세 가지 핵심 영역`
- 고친 예: `Git이 관리하는 폴더 안에서 파일이 이동하는 세 가지 핵심 영역`
- 이유: 작업 공간·스테이징·로컬 저장소는 저장소 단위 개념이다. 범위를 넓게 쓰면 `.git` 바깥 파일도 추적된다고 오해한다(`879bc91`).

### 2-4. `~의 필요성` 패턴을 쓰지 않는다
- 규칙: 명사형 `~의 필요성` 대신 질문형 소제목(`왜 … 할까`)이나 동사형(`…가 왜 필요한지 이해한다`)으로 쓴다.
- 잘못된 예: `## 버전·형상 관리의 필요성` / `SCM의 필요성을 이해한다.`
- 고친 예: `## 왜 버전·형상 관리를 할까` / `SCM가 왜 필요한지 이해한다.`
- 이유: 번역투 명사 나열을 줄이고 학습자가 답해야 할 질문으로 바꾼다(#53).

### 2-5. 안내는 `참고한다`로 쓴다
- 규칙: 다른 부록·STEP·문서를 안내하는 문장은 `…을 참고한다`로 끝낸다. `참조한다`는 쓰지 않는다. 개념어(`원격 참조`)와 링크 라벨(`명령어 참조:`)은 예외다.
- 잘못된 예: `상세한 Git 명령 옵션은 [명령과 옵션 일람](…) 부록을 참조한다.`
- 고친 예: `상세한 Git 명령 옵션은 [명령과 옵션 일람](…) 부록을 참고한다.`
- 이유: `참조`는 값·대상을 가리킨다는 기술 용어에 가깝고, 학습자에게 읽어 보라고 안내하는 말은 `참고`가 자연스럽다(사용자 지적).

## 3. 제목·구조

### 3-1. 차시 표기를 쓰지 않고 STEP NN은 표시 계층이 붙인다
- 규칙: 원본 H1·본문·교차 링크에 `N차시`를 쓰지 않는다. 순서 라벨 `STEP NN`은 사이트 헤더·사이드바가 파일 순서로 생성하며 교차 링크 텍스트는 `STEP 01 버전 관리의 세 영역` 형식을 쓴다.
- 잘못된 예: `# 1차시. 개발자를 위한 첫 번째 안전망: VCS/SCM과 Git의 세 영역` / `## 이 차시에서 하는 일`
- 고친 예: `# 버전 관리의 세 영역` / `## 학습 목표`
- 이유: 순서는 메타데이터이고 제목은 개념이다. 원본에 순서를 박으면 재배치할 때마다 본문을 고쳐야 한다(#44·`d066d1e`).

### 3-2. 제목은 개념, 부제는 목적, 명령어는 태그
- 규칙: H1은 짧은 한국어 개념명(13자 안팎), frontmatter `subtitle`은 `~한다`로 끝나는 목적 문장 한 개, 명령어·핵심 용어는 frontmatter `tags` 배열에 둔다. 부제에 명령어를 섞지 않는다.
- 잘못된 예: `# config·init·status·add` + `subtitle: "config·init·status·add로 Git 저장소를 만들고 파일을 추적한다."`
- 고친 예: `# 저장소 준비와 파일 추적` + `subtitle: "Git 저장소를 만들고 파일을 추적한다."` + `tags: ["config", "init", "status", "add"]`
- 이유: 제목은 목차·OG·공유 제목에, 태그는 헤더 칩에 쓰이므로 역할을 나눠야 한 곳만 고치면 된다(#44·#53).

### 3-3. 중간 제목(H2·H3)은 16자 이하
- 규칙: 공백·문장부호 포함 16자 이하. 인라인 코드의 글자도 센다.
- 잘못된 예: `## 이력 수정과 불필요한 파일 배제가 필요한 이유`(25자) / `### .gitignore의 동작 원리와 작성 규칙`(24자)
- 고친 예: `## 이력을 고치고 배제하는 이유`(15자) / `### .gitignore 작성 규칙`(16자)
- 이유: 모바일 사이드바·목차에서 줄바꿈 없이 읽히고 PDF 목차 폭에 맞는다(#44 2차 제목 정리).

### 3-4. 고정 소제목 용어
- 규칙: 공통 섹션 이름은 `학습 목표`·`주의할 점`·`트러블 슈팅`·`체크리스트`·`핵심 내용 퀴즈`를 쓴다. 옛 이름 `정보 누출 방지`·`오류 복구`·`확인법`·`확인 방법`·`퀴즈 풀기`는 쓰지 않는다. 그 외 관례 섹션은 `따라하기`·`Git 명령`·`에이전트 요청 예시`다.
- 잘못된 예: `## 정보 누출 방지` / `## 오류 복구` / `## 확인법`
- 고친 예: `## 주의할 점` / `## 트러블 슈팅` / `## 체크리스트`
- 이유: 모든 STEP에서 같은 이름이어야 학습자가 위치를 예측하고 앵커 링크가 안정된다(#53).

### 3-5. 일정·환경 메타 줄을 본문에 쓰지 않는다
- 규칙: `Day N · 시간`, `선수 학습:`, `준비 도구:`, `저장소:`, 점심시간 안내 줄을 본문에 두지 않는다. D1 호환에 필요한 `day`·`schedule`은 frontmatter에만 둔다. 설치 링크는 `learn-site/.vitepress/install-links.json`과 frontmatter `downloads`로 관리한다.
- 잘못된 예: `Day 1 · 09:00–09:45 (수업 45분)` / `선수 학습: 웹 개발 기초` / `점심시간 안내: 12:00–13:00` / `저장소: portfolio-web`
- 고친 예: (삭제) 또는 frontmatter `day: 1`, `schedule: "09:00–09:45 (수업 45분) / …"`
- 이유: 강의 일정은 운영 정보라 게시 콘텐츠와 분리한다. 본문에 두면 일정이 바뀔 때마다 PDF seal을 깨야 한다(#44·#53). 서술 문장 안의 `Day 1의 STEP 01~06 공식 일정이 완료되었다`(STEP 06)는 메타 줄이 아니므로 허용한다.

### 3-6. 보충 탭 없음·부록 번호 미표기
- 규칙: 부록 원본 H1·사이드바·페이지 제목에 `부록 N.` 번호를 표기하지 않는다. 순서는 파일명 접두 `NN-`로만 정한다. 보충은 사이드바에 탭을 두지 않는다(`062228d`). 사이드바 아이콘은 `learn-site/.vitepress/nav-icons.json`에 `appendix/NN-slug` 키로 등록하고 SVG는 `theme/icons/nav/`에 둔다.
- 잘못된 예: `# 부록 2. Git 명령·옵션`
- 고친 예: `# 명령과 옵션 일람`
- 이유: 3-1과 같은 이유로 번호는 메타데이터다. 번호를 표시하지 않으면 부록을 끼워 넣거나 순서를 바꿔도 본문·링크 텍스트를 고치지 않는다(#43·#44·#56).

### 3-7. 같은 안내를 반복하지 않는다
- 규칙: 모든 STEP에 같은 안내(보충 링크 등)를 반복해서 넣지 않는다. 공통 안내는 과정 첫 페이지나 해당 부록 한 곳에 둔다.
- 잘못된 예: STEP 01~12 끝마다 `보충 자료는 … 를 참고한다.`
- 고친 예: (삭제) 과정 첫 페이지 목차와 부록 링크로 대체
- 이유: 12곳을 함께 고쳐야 하는 중복이 생기고 학습 흐름을 끊는다(`4cdaac1`).

### 3-8. 인라인 코드 안의 백틱
- 규칙: 백틱 키 자체를 표기할 때는 이중 백틱으로 감싸거나 코드 블록으로 뺀다. 한글 조사가 바로 붙는 강조는 strong 태그를 쓴다(`scripts/lint-markdown.cjs`). 강의 원본은 사이트 페이지로도 빌드되므로 닫히지 않은 HTML 태그를 본문에 두지 않는다.
- 잘못된 예와 고친 예:

```text
잘못된 예: 단축키(`Ctrl + ` ` 또는 `Ctrl + ~`)
고친 예:   단축키(``Ctrl + ` `` 또는 `Ctrl + ~`)
```

- 이유: 백틱이 구분자로 해석돼 글자가 사라진다(#43). 열린 태그는 Vue 컴파일 단계에서 빌드를 깨뜨린다.

## 4. 검사 스크립트

결정론적 항목(존댓말 종결, `필요성`·`차시`·`혼선`·`점심`·`낳는다`, 메타 줄, 옛 소제목, 16자 초과 H2/H3)은 `scripts/content-lint.mjs`가 검사한다. 줄 단위 판정은 `scripts/content-lint-check.mjs`, 규칙 값은 `scripts/content-lint.rules.json`에 있고, 코드 블록·인라인 코드·frontmatter·링크 대상은 검사하지 않는다. `docs/lecture/index.md`(미게시 강사용 일정표)는 `ignore`로 제외한다. CI에는 연결하지 않았다.

```bash
node scripts/content-lint.mjs docs/lecture          # 디렉터리 전체
node scripts/content-lint.mjs docs/lecture/01-environment.md
```

위반이 있으면 `파일:줄: 종류: 내용`을 stderr로 출력하고 종료 코드 1을 돌려준다. 2-1·2-2·2-3·3-2처럼 문맥 판단이 필요한 규칙은 리뷰어가 본 문서를 기준으로 확인한다.
