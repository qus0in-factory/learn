# Git·GitHub 교안과 SEO 보강 회고 및 부검

2026년 11월 14일 진행한 [#117](https://github.com/qus0in-factory/learn/issues/117)의 교안·태그·SEO 개선을 돌아본다. 핵심 교훈은 코드 검증, 운영 값으로 만든 배포 산출물, 공개 응답, 검색 도구의 판정을 각각의 완료 조건으로 관리해야 한다는 점이다. 로컬 검사와 배포가 성공해도 검색 서비스가 요구하는 속성이나 소유자 작업까지 끝난 것은 아니었다.

## 유지할 작업 방식

### 구현과 리뷰의 근거를 나눈다

태그 분리에서는 JSON 데이터, 본문 링크, Vue 화면, Markdown 내보내기를 함께 확인했다. 과정 판별 정리에서는 태그를 바꾸기 전 리팩터링만의 빌드를 dev와 대조해 head·JSON-LD·본문·Markdown·sitemap의 동일성을 확인했다. 이후 태그 변경에 따른 차이를 별도로 설명할 수 있었다.

읽기 전용 리뷰에서 발견한 문제는 수정 커밋과 재확인 보고로 연결했다. 실제 스크린샷, Git 명령의 종료 조건, 학습 순서처럼 자동 린트가 판단하지 못하는 내용은 원본과 실행 결과를 대조했다. 다음 작업에서도 검사 통과와 내용 검토를 따로 보고한다.

### 소유자 작업과 자동화 작업을 분리한다

Search Console의 요청과 계정 확인은 #119에, 프로필 문구와 링크 반영은 #120에 남겼다. 공개 프로필 README는 먼저 읽기만 하고 초안을 이슈에 제시했다. 반영 확인 댓글이 올라온 뒤 이슈가 닫혔다. 자동화가 실행하지 않은 외부 작업을 완료로 표시하지 않는 방식은 유지한다.

### 배포 SHA와 공개 응답을 연결한다

두 배포 모두 정확한 SHA의 CI와 Worker version을 기록하고 별도 readback 결과를 남겼다. `readback.sh`의 HTTP 상태·Location·Cache-Control 기록과 정적 자산·PDF의 크기·SHA 검증은 서로 다른 증거로 관리했다. 문서 기록 커밋과 실제 배포한 커밋도 구분했다.

## 재작업 부검

### CI의 Node 패치 차이로 JSON 계약이 깨졌다

로컬에서 통과한 테스트가 dev CI에서는 44개 중 3개 실패했다. 카탈로그의 강의·퀴즈 배열이 문자열이 되면서 배열 길이 대신 문자열 길이가 관찰됐고, `version`이 사라졌다. 뒤의 빌드와 산출물 검사는 실행되지 못했다.

조사 기록 `ci-fail.md`는 직전 성공 환경의 Node 26.13.0과 실패 환경의 26.13.1을 구분했다. 로컬 Node 24.22.1의 SQLite는 3.53.4, CI와 같은 Node 26.13.1은 SQLite 3.54.1이었다. 후자에서 `json_object`에 넣는 스칼라 서브쿼리 결과의 JSON subtype이 유지되지 않아 TEXT로 삽입되는 것을 재현했다. 해당 SQL은 태그·본문 변경 구간에서 바뀌지 않았다.

[a1d267f](https://github.com/qus0in-factory/learn/commit/a1d267f5414d6e44e8a56a8b8d781801d6c27a76)는 meta·lectures·quiz·lessons의 서브쿼리 바깥을 `json((SELECT …))`로 감쌌다. 조사·수정 보고에서 두 Node 환경 모두 44/44 통과를 확인했다. 테스트 기대값이나 CI 워크플로는 바꾸지 않았다. D1 자체의 SQLite 버전이나 같은 장애 발생 여부까지 확인한 결과는 아니다.

다음에는 CI만 실패하면 정확한 Node와 내장 라이브러리 버전, 실패 단계부터 맞춘다. 최근 콘텐츠 변경을 원인으로 단정하거나 테스트 기대값을 낮추기 전에 응답의 타입과 계약을 대조한다.

### 검증용 산출물과 운영 산출물을 구분해야 했다

기본 로컬 검증은 운영 CDN·카카오 변수를 직접 주입하지 않는다. 그 산출물만 준비한 채 운영 배포 가드를 통과하려는 경로는 실제 가드 조건과 맞지 않는다. 관련 스크립트는 CDN base와 유효한 카카오 키, 번들 내 같은 키, 자산의 CDN URL을 검사한 뒤 원격 크기·SHA 검증으로 넘어가도록 돼 있다. 실패 횟수나 당시 첫 오류 메시지는 보존된 배포 성공 로그만으로 확정하지 않았다.

운영 값을 보호된 env-file로 주입해 다시 빌드하는 절차를 배포 스킬에 적었다. 이 문구를 리뷰하면서 `--env-file=<메인>/.env.local`의 꺾쇠가 셸 리다이렉션이 되는 문제도 발견했다. [3d7ad22](https://github.com/qus0in-factory/learn/commit/3d7ad221761570680a265facfe3e00d35434aea6)에서 ENV_FILE 정의와 인용된 인자, 도구별 dry-run·실제 업로드·HTTP readback을 구분했다.

다음에는 로컬 검증 통과와 운영 재빌드를 별도 단계로 확인한다. 가드를 끄지 않고 실패 조건에 맞는 산출물을 준비한다. 이미 운영 변수가 있는 셸도 있으므로 검증 스크립트가 항상 키를 제거한다고 설명하지 않는다. 키 값은 기록하지 않고 주입 경로와 검사 결과만 남긴다.

### JSON 파싱 성공이 Course 유효성을 뜻하지 않았다

로컬 보고에서는 70개 JSON-LD의 파싱 성공과 최상위 유형, hasPart 등을 확인했다. 이후 #119의 리치 결과 테스트에서 순한맛 레슨의 Course에 name·description이 없다는 오류가 발견됐다. 탐색경로가 유효한 것과 Course 항목이 유효한 것은 별개의 판정이었다.

원인은 공통 생성기가 레슨의 `isPartOf`를 `@type: Course`와 `@id`만 가진 객체로 선언한 데 있었다. 이 경로는 git 과정에도 같았다. JSON 문법은 맞았지만, 중첩된 타입의 필수 속성을 검증하지 않아 놓쳤다.

[3e520e2](https://github.com/qus0in-factory/learn/commit/3e520e21fa1a8fd652e05fd02824c260923fb5d9)는 레슨의 과정 연결을 `@id`만 있는 참조로 바꾸고 과정 첫 페이지의 완전한 Course에 같은 ID를 부여했다. 공통 publisher의 Organization ID도 연결했다. 후속 검사에서는 JSON-LD 70개 파싱 오류 0, 재귀 검사한 Course 2개의 name·description·provider 위반 0, 레슨 60개의 참조 일치를 확인했다.

다음에는 구조화 데이터 변경 시 중첩 노드까지 순회해 타입별 필수 속성과 참조 대상을 확인한다. 배포 후에는 Google 도구의 판정을 별도로 기록한다. 로컬의 파싱 성공을 외부 리치 결과 오류 0으로 바꾸어 보고하지 않는다.

### 워크트리에 검증 도구가 없거나 실행 경로가 달랐다

초기 작업에서는 메인에만 있던 미커밋 하네스와 `scripts/verify-local.sh`가 워크트리에 없었다. 검증 진입점이 준비되지 않아 작업을 이어 갈 수 없었고, [d34fbe2](https://github.com/qus0in-factory/learn/commit/d34fbe205cefc6e0e8271b880fe334c9f626560e)로 하네스와 스크립트를 커밋한 뒤 각 브랜치에 반영했다.

그 뒤에도 워크트리의 `course-site/node_modules` symlink와 pnpm의 의존성 사전 확인이 충돌했다. 일부 보고는 경고 뒤 빌드가 성공했고, 다른 보고는 `ERR_PNPM_UNSAFE_MODULES_DIR`로 중단됐다. 경고와 실제 실패를 같은 사건으로 묶지 않고 종료 코드와 실패 단계를 구분해야 했다.

[22a3977](https://github.com/qus0in-factory/learn/commit/22a3977bbe544a944e82ff5bf2210b2e32bb274a)는 verify-local의 빌드를 pnpm exec에서 기존 배포 문서와 같은 직접 Node 실행으로 바꿨다. 워크트리와 메인에서 동일한 검증 단계를 통과한 보고를 남겼다. CI의 정상 의존성 설치 경로는 수정하지 않았다.

다음에는 작업 분배 전에 하네스 커밋과 워크트리 반영, 의존성 링크, 검증 스크립트 존재를 확인한다. 다른 경로에서 통과한 결과를 지정 검증 명령의 통과로 대신하지 않는다.

### 소유 파일 목록이 실제 의존 경로를 다 담지 못했다

최초 설계표의 T1 소유 목록에는 `markdown-widgets.mjs`가 빠져 있었지만, easy 태그 페이지의 Markdown 출력도 과정별 집계를 사용해야 했다. 실제 T1 커밋은 이 파일을 포함한다. 과정 판별 정리도 `markdown-glossary.mjs`와 `seo-course-parts.mjs`가 함께 바뀌어야 했고, SEO 잔여 작업의 최종 보고에는 이미지와 alt를 함께 고르는 OG 파일이 포함됐다.

이 문제는 수정자가 임의로 범위를 넓혀 해결할 일이 아니었다. 공통 함수의 호출자와 내보내기 경로를 분배 전에 따라가고, 다른 트랙과 소유권을 맞추는 단계가 필요했다. 최종 작업 보고와 커밋은 확인했지만 T1·refactor·seo-c의 초기 차단 보고 일부가 완료 보고로 덮어써져, 세 트랙의 중단 횟수와 시점, 대기 시간을 파일만으로 다시 집계할 수는 없었다.

다음에는 소유 목록에 직접 수정할 파일뿐 아니라 import로 연결된 호출자, Markdown 내보내기, 같은 데이터를 사용하는 화면까지 적는다. 차단 보고는 완료 보고로 덮지 않고 결정 기록과 함께 보존한다. 재개 시 새로 허용한 파일을 명시하며 다른 작업자의 변경을 건드리지 않는다.

### 대기 반환을 작업 완료로 해석할 근거가 부족했다

watcher의 조기 반환도 이번 회고의 확인 대상이었다. 이번에 대조한 작업 보고와 커밋에는 당시 반환 메시지, 대상 작업의 상태, 반환 시각을 함께 입증하는 기록이 없었다. 이 항목의 원인과 횟수, 실제 영향은 확정하지 않는다.

대기 호출이 돌아왔다는 사실과 대상 작업이 끝났다는 사실은 같은 증거가 아니다. 다음에는 watcher 결과에 완료·진행 중·입력 필요 상태를 구분하고, 완료라면 커밋·검증 결과·종료 코드를 연결한다. 자료가 없는 사건을 다른 실패의 원인으로 합산하지 않는다. 이 기준은 재발 방지 제안이며, 당시 watcher 구현을 수정했다는 뜻은 아니다.

### 총괄과 리뷰 역할을 지침으로 다시 고정했다

작업 중 역할 지침을 정정한 기록은 [604f11d](https://github.com/qus0in-factory/learn/commit/604f11d437c2fa676ea22d9e56d8302c86ffcdb4)와 통합 2단계 보고에 남았다. 총괄은 분배를 맡고 대기는 watcher, 리뷰·최종 검수는 구현자와 다른 워커가 맡으며 `work-reviewer`는 자제하도록 바뀌었다.

이 기록은 역할 경계가 다시 명문화됐음을 보여 준다. 다만 개별 도구 호출을 모두 보존한 자료는 아니므로, 누가 어느 조사·배포·검수를 직접 수행했는지나 그에 따른 시간 손실까지 단정하지 않는다. 문제를 특정 사람의 태도보다 분배와 완료 기준의 부족으로 다룬다.

다음에는 작업을 맡길 때 실행·검증·리뷰·통합의 책임과 결과 파일을 함께 정한다. 총괄이 결과를 기다리는 방식과 구현자와 다른 리뷰 담당을 유지하고, 승인된 배포도 담당 실행자와 readback 검토자를 명확히 연결한다.

### 알림 본문과 전송 완료의 증거가 분리되지 않았다

작업 디렉터리에는 1차·#117 종료·#118·#119·#120의 Discord 알림 본문이 남아 있다. #119·#120의 후속 변경을 묶은 문안도 확인했다. 그러나 본문 파일만으로 누락 정정 전후의 실제 전송 시각이나 웹훅 성공 응답까지 입증할 수는 없다. 알림 누락의 정확한 횟수는 기록하지 않는다.

후속 하네스 커밋 `cd02530`에는 이슈 생성·배포·종료 시 `discord-notify`를 따르도록 하는 포인터가 추가됐다. 이는 별도 하네스 브랜치의 커밋으로 확인했으며, 이 회고 브랜치에 해당 규칙을 병합하거나 새 알림을 전송한 것은 아니다.

다음에는 문안 작성, dry-run 확인, 실제 전송 결과를 나누어 기록한다. webhook 값은 보존하지 않고 전송 성공 여부와 보고 대상만 남긴다. 사이트 readback 통과나 이슈 생성 성공을 알림 전송 완료로 대신하지 않는다.

### 사실과 실행 조건은 리뷰에서 다시 교정했다

| 발견한 문제 | 놓친 조건과 영향 | 확인한 조치 | 다음에 지킬 기준 |

| git 버전 확인 명령의 본문·alt 일괄 치환 | 화면에는 `git -v`가 있는데 설명을 `git --version`으로 바꿔 실제 기록과 모순됐다 | `9844daa`에서 당시 명령을 복원하고 실습 권장 명령을 따로 안내했다 | 이미지에 보이는 사실과 앞으로 권장하는 절차를 나눈다 |
| `git branch -M main` 안내 | 같은 이름의 기존 브랜치를 덮어써도 되는지 확인하는 조건이 약했다 | `2d01d9e`에서 기존 main을 덮어써도 되는지 먼저 확인하도록 경고를 보강했다 | 강제 옵션의 효과와 실행 전 확인을 함께 적는다 |
| vim의 `:q!`를 커밋 취소로 단순화 | 편집기가 vim이라는 전제와 미리 채워진 메시지, 빈 메시지의 종료 조건이 빠졌다 | `96684d7`에서 트러블 슈팅으로 합치고 확실한 중단 `:cq`와 빈 메시지 동작을 설명했다 | 편집기 종료와 Git 명령의 성공·중단을 따로 재현한다 |
| Pages 절과 예시의 배치 | 계정 사이트·docs 폴더 설명 뒤에 프로젝트 사이트 예시가 와 흐름이 섞였다 | `0eb60c9`에서 기존 공개 예시 뒤에 계정 사이트 절을 두었다 | 새 절은 앞 단계의 결과를 확인한 뒤에 배치한다 |

이 수정들은 같은 린트·빌드 검사를 통과한 초안에도 남아 있었다. 리뷰에서는 타입과 링크 존재뿐 아니라 화면의 실제 내용, 명령의 선행 상태, 다시 실행했을 때의 결과, 학습자가 읽는 순서까지 확인해야 했다.

## 다음 개정에서 적용할 기준

- CI 실패는 정확한 런타임과 내장 라이브러리 버전으로 재현한 뒤 응답 타입을 점검한다. 기대값이나 CI를 먼저 바꾸지 않는다.
- 워크트리를 만들면 커밋된 하네스와 검증 도구, 의존성 링크, import를 포함한 파일 소유권을 먼저 확인한다.
- 완료 보고를 로컬 검증, 운영 빌드, 배포, readback, 외부 도구 판정, 소유자 작업, 알림 전송으로 구분한다.
- JSON-LD는 파싱과 타입별 필수 속성·중첩 노드·ID 참조를 각각 검사한다. 검사 범위를 넓히더라도 새 테스트·CI는 요청 없이 추가하지 않는다.
- 회고 자료의 최초 차단 보고와 결정 이력을 보존한다. 최종 완료 보고로 덮어쓰면 반복 횟수와 원인을 다시 확인하기 어렵다.
- 본문 수정과 고정 PDF 교체는 별도 작업이다. 차이가 생겼으면 영향받는 입력과 승인된 후속 이슈를 연결한다.
- Google 색인·검색 노출과 외부 계정 작업은 실제 확인한 결과만 완료로 표시한다. 문서나 코드의 준비 상태로 대신하지 않는다.

이번 문서는 `docs/operations`에 두었다. 이 경로는 사이트 빌드와 PDF 입력 hash 대상에서 제외되므로, 회고 문서만 바꾼다고 사이트를 배포하거나 PDF를 다시 만들지 않는다.
