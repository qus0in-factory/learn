# Git 교안과 PDF 보강 회고 및 부검

2026년 11월 7일 진행한 교안 보강과 PDF 배포를 돌아본다. 핵심 교훈은 설명을 늘리는 일, 강의에 맞게 편집하는 일, 공개본을 교체하는 일을 각각의 완료 조건으로 관리해야 한다는 점이다. 장수와 자동 검사만으로는 이 세 가지를 함께 판단할 수 없었다.

## 결과와 확인 범위

기존 PDF 12개 179장을 268장으로 보강했다. 실습 저장소와 메모의 명령·프롬프트를 대조하고, 검토한 화면을 교안과 PDF에 반영했다. PDF의 퀴즈·정답·자료 안내는 제거했고, Mermaid는 코드와 그 코드로 생성한 결과 그림만 남겼다.

배포한 커밋은 [8fa748f](https://github.com/qus0in-factory/learn/commit/8fa748f4a0f6f13a658ff0f627c9eceeb4d4f981)이며, [동일 SHA의 CI](https://github.com/qus0in-factory/learn/actions/runs/42365445102)가 성공했다. PDF 12개와 정적 자산 256개의 원격 크기·SHA를 확인했고, 공개 PDF의 리다이렉트·응답·해시, 사이트 버튼과 카탈로그의 URL 일치도 검증했다. 과정 첫 화면과 스크린샷 10개도 공개 응답으로 확인했다. 현재 revision과 Worker version은 [운영 목차](index.md)를 따른다.

## 유지할 작업 방식

### 메모의 조건을 결과와 함께 확인한다

교안의 주제만 보고 프롬프트를 새로 요약하면 학습에서 중요한 조건이 빠질 수 있었다. 소개 문구의 64자 제한과 추가 수정 금지, 프로필의 256자·기술 배지, 무채색 중심·강조색 한 가지 같은 조건을 메모와 대조해 복원했다.

다음 개정에서도 요청의 대상·범위·제약을 먼저 확인한다. 프롬프트 옆에는 생성 결과를 판단할 기준을 둔다. 문구 수정이면 diff, 소개 페이지면 화면과 색상, 이슈 계획이면 배경·완료 조건·분류를 확인한다. 프롬프트의 파일명은 문서 역할이나 선택한 대상으로 바꿀 수 있지만, 길이와 수정 범위 같은 조건은 유지한다.

### 보호할 정보와 학습할 정보를 구분한다

스크린샷은 포함하기 전에 직접 확인했다. 인증 정보가 중심인 화면은 제외하고, 계정·기기 식별 정보는 불투명하게 가리거나 필요한 영역만 잘랐다. 마스킹한 사본을 웹 교안과 PDF에 사용해 원본을 반복해서 가져오는 일을 줄였다.

배포 키는 보호된 env-file로 주입하고 값은 출력하거나 커밋하지 않았다. 이후에도 이미지 확인과 텍스트 확인을 별도로 수행한다. 이미지 속 정보는 텍스트 검색만으로 걸러지지 않는다.

### 공개 응답으로 배포를 끝낸다

검토본과 배포용 PDF의 공백을 정규화한 추출 텍스트가 일치하는지 확인한 뒤 새 revision으로 고정했다. 이전 R2 객체를 보존하고, 새 PDF의 업로드와 원격 검증이 끝난 후 Worker와 D1을 전환했다.

정적 자산은 읽기 검증을 병렬화하되 내려받은 바이트로 크기·SHA 검증을 유지했다. PDF 업로드, Worker 배포, D1 적용의 순서는 기존 가드를 따랐다. 마지막에는 로컬 산출물의 성공 로그에 더해 공개 URL의 PDF 바이트와 사이트·카탈로그를 확인했다.

## 재작업 부검

### 설명 보강과 구성 추가를 혼동했다

설명이 생략됐다는 요청에 대응하면서 퀴즈·정답·원문 링크까지 일괄 추가했다. 날짜·출처, 특정 파일명과 사례를 회고하는 표현도 화면 해설에 반복됐다. 사용자는 강의용 PDF에서 이 구성을 제외하도록 정정했고, 여러 차례 재편집과 재생성이 필요했다.

기존 덱 계약이 12–15장으로 제한된 것은 확인된 사실이다. 이 제약이 과도한 축약에 기여했을 가능성은 있지만, 제한을 늘리는 것만으로 편집 문제가 해결되지는 않았다. 보강 과정에서도 웹 교안의 구성과 강의용 PDF의 필요 범위를 같게 취급한 판단이 재작업을 만들었다.

다음에는 빠진 내용을 명령의 전제조건, 실행 순서, 확인 결과, 오류 대응으로 먼저 나눈다. 새 구성은 사용자의 용도와 기존 편집 기준에 맞을 때 추가한다. 대표 덱의 설명·명령·그림·프롬프트를 검토한 뒤 공통 구성을 다른 덱에 적용한다.

### 구조 검사를 통과해도 명령은 실패할 수 있었다

| 발견한 문제 | 실패하는 이유 | 교정한 방식 |
| --- | --- | --- |
| 다른 계정의 저장소를 복제한 뒤 push하는 예 | 학습자에게 쓰기 권한이 없을 수 있다 | 본인 계정과 프로필 저장소를 전제로 바꿨다 |
| 같은 태그 생성 명령의 반복 | 두 번째 생성에서 이름이 이미 존재한다 | 후속 단계는 태그 조회와 확인으로 바꿨다 |
| 병합을 마친 브랜치로 fast-forward를 다시 기대 | 이미 반영됐으면 `Already up to date`가 나온다 | 병합 전제와 반복 실행 결과를 설명했다 |
| URL에 꺾쇠 자리표시자를 그대로 사용 | 셸이 리다이렉션으로 해석할 수 있다 | 계정·저장소 변수를 사용했다 |
| URL 중간의 줄바꿈 뒤에 들여쓰기 | URL이 여러 인자로 나뉠 수 있다 | 주소를 변수로 구성하고 인자 경계에서 줄을 나눴다 |

JSON 파싱과 레이아웃 검사는 명령의 권한·선행 상태·반복 실행까지 판단하지 못한다. 명령을 검토할 때는 시작 브랜치, 커밋 유무, 앞 단계의 변경, 다시 실행했을 때의 결과를 함께 읽어야 한다. 프롬프트 검토와 명령 검토도 별도로 수행한다.

### 글꼴과 레이아웃 검사는 편집 검토를 대체하지 못했다

한글 줄바꿈, 긴 명령행, 작은 화면 이미지가 가독성 문제로 이어졌다. `word-break: keep-all`을 일부 텍스트 요소에만 적용한 상태에서 전체 덱과 하위 요소로 범위를 넓혔고, 링크의 덮어쓰기 규칙도 정리했다. 긴 명령은 인자 경계에서 나누고, 한 개의 코드 블록은 한 열로 표시했다. 화면 이미지와 해설도 별도 장으로 나눴다.

검사에서는 넘침 외에 `statement`의 강조 문구가 본문에 없는 구조 오류도 발견했다. 수정 후 폰트 fallback·경계·겹침 검사를 다시 수행하고, PDF의 페이지 규격·추출 텍스트·단어 좌표를 확인했다. 대표 페이지는 이미지로 열어 읽었다.

자동 검사는 잘림과 구조 오류를 찾는 데 유효했다. 어떤 설명이 불필요한지, 프롬프트의 조건이 빠졌는지, 이미지가 학습에 충분히 읽히는지는 별도의 편집 검토가 필요했다.

### 병렬 작업의 완료 기준이 충분히 구체적이지 않았다

원고를 덱별로 나누고 수정할 파일 범위를 정해 충돌을 줄였다. 그러나 JSON 파싱과 diff 확인만으로 완료를 보고한 원고에서도 명령행 넘침과 설명의 전제 오류가 남았다. 일부 작업은 파일 저장보다 설계·표현 검토가 길어졌고, 남은 덱을 재분배해 진행했다.

다음에는 담당 파일뿐 아니라 저장된 원고, 조건을 보존한 프롬프트, 명령의 전제, 렌더링 결과를 완료 기준으로 전달한다. 진행은 장수와 변경 파일로 확인하고, 최종 통합 담당자가 전체 덱의 용어와 실행 흐름을 대조한다. 읽기 전용 검토와 파일 수정 담당도 구분한다.

### 로컬 완료와 공개 반영을 더 분명하게 보고해야 했다

초기 완료 보고는 로컬 PDF 링크를 제공했고, 사용자가 배포 여부를 다시 확인했다. 공개본은 이 시점까지 이전 revision이었으며, 이후 배포 지시를 받아 교체했다.

다음 완료 보고에는 원고 수정, 로컬 생성·검증, 공개 배포·readback 중 어디까지 끝났는지를 명시한다. 배포가 요청되면 세션에서 받은 승인을 이어서 적용하고, 기존 절차의 승인 문구를 이유로 같은 범위를 다시 묻지 않는다. 공개 URL 검증 전에는 배포 완료로 보고하지 않는다.

### 설치 경고와 배포 실패를 같은 사건으로 취급하지 않는다

배포용 worktree는 기존 의존성 디렉터리를 심볼릭 링크로 연결했다. `pnpm` 실행 전 의존성 확인에서 hoist 디렉터리가 실제 디렉터리가 아니라는 경고가 발생했지만, 이어진 VitePress 빌드와 Worker·D1 배포는 성공했다. 공개 응답의 해시 검증도 통과했다.

이 경고는 worktree의 링크 구성과 의존성 사전 확인의 관계를 따로 점검할 항목이다. 이번 결과만으로 설정 충돌이 해결됐다고 보지는 않는다. 재발하면 실패 단계·종료 코드·산출물을 먼저 확인하고, 원인 확인 없이 CI·lockfile을 바꾸거나 같은 배포를 반복하지 않는다.

## 다음 개정에서 적용할 기준

- PDF에는 퀴즈·정답·원문 및 자료 안내를 자동 추가하지 않는다. 날짜·출처와 사례를 회고하는 표현도 제외한다.
- Mermaid는 코드와 그 코드로 생성한 결과만 보여 준다. 문법 설명을 별도 장으로 늘리지 않는다.
- 메모의 프롬프트 제약을 유지하고 파일명은 필요한 명령·설정·진입점에 한해 사용한다.
- 한글 단어를 유지하는 줄바꿈과 기본 글자 크기를 유지한다. 넘치면 문장·명령·페이지를 나누고 다시 렌더링한다.
- 편집 검토, 실행 전제 검토, 구조·레이아웃 검증을 각각 수행한다. 하나의 통과를 다른 항목의 통과로 대신하지 않는다.
- 배포는 원본 커밋, 고정 revision, 배포 커밋, 공개 응답을 연결해 기록한다. 문서 정리 커밋과 배포한 커밋을 혼동하지 않는다.
- 요청하지 않은 CI·단위 테스트·e2e는 추가하지 않는다. 확인된 환경 개선은 재현 범위와 변경 필요성을 정리한 후 별도로 다룬다.

이번 회고는 `docs/operations`에 두었다. 이 경로는 사이트 빌드와 PDF source hash 대상에서 제외되므로, 회고 문서의 변경만으로 공개 PDF를 재생성하거나 재배포하지 않는다.
